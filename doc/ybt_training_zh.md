# YBT 四足：Isaac Gym 训练接入说明

## 1. 已完成的内容

YBT 已注册为四个独立任务，复用仓库的四足观测、PD 力矩控制和 PPO 训练流程：

- **`ybt`**：纯四足（61.67 kg，12 个可动关节）
- **`ybt_arm`**：带 RM65-B 机械臂的四足（68.84 kg，18 个可动关节），机械臂冻结当配重，
  详见第 6 节
- **`ybt_arm_stand`**：同一台机器人站着不动，机械臂按脚本摆动，腿负责稳住机身，详见第 7 节
- **`ybt_arm_walk`**：机械臂照样摆动，腿同时执行走/横移/转向指令，详见第 8 节

当前范围仅包含 **Isaac Gym 平地训练与 Play/策略导出**，不包含 YBT 的 MuJoCo 或实机部署。

## 2. 为什么不能直接复制 Go2 配置

- YBT 模型总质量约 **61.67 kg**，控制增益不能简单沿用 Go2 的 `20 / 0.5`。
- YBT 大腿、膝关节轴为 `0 -1 0`；站姿使用 **大腿 -0.8 rad、膝关节 +1.6 rad**，而不是 Go2 的正大腿、负膝角。
- 膝关节的 URDF 限位约为 `[1.0297, 2.7227]` rad。原环境以默认角乘 `0.5..1.5` 复位时，可能得到 `0.8` rad，越过下限。YBT 改为默认角加 **±0.05 rad** 随机扰动，再夹到软限位内，其他机器人的复位逻辑不变。
- YBT 的机身名是 `trunk`，跌倒接触终止条件必须匹配这个名称；保留四个 `*_foot` 刚体用于接触和足端奖励。
- 默认角按 **关节名称**匹配。动作顺序以 Isaac Gym 加载后的 `dof_names` 为准，不由配置字典的排列决定。本机实测顺序是 FL、FR、RL、RR，每条腿 hip、thigh、calf。

控制初值：hip `Kp=100 / Kd=3`，thigh/calf `Kp=150 / Kd=4`，动作缩放 `0.25`。
这些是已跑通短测的**仿真起始参数**，并非实机增益或已经优化到最优的控制参数。
出生机身高度 `0.55 m`，奖励目标高度 `0.50 m`。

针对首轮训练暴露出的**走路拖沓/迈不开脚、走几秒就歪**，做了如下调整：

- `heading_command = True`：恢复朝向闭环。基类（go2 等）默认就开，原先只追踪偏航**速率**，残留的小偏航率几乎不受惩罚却会累积成明显偏航。注意：开启后偏航由"朝向误差"闭环生成。`play.py` 为此提供两种互斥的转弯方式：`--cmd_heading=<度>` 指定目标朝向（机器人转过去并保持），`--cmd_wz=<rad/s>` 指定固定转速（此时会临时关掉朝向环，否则该值每一步都被覆盖）。只给 `--cmd_vx/--cmd_vy` 时目标朝向锁在 0，机器人保持出生朝向走直线。
- `feet_clearance` 奖励（`YBTRobot._reward_feet_clearance`）：摆动腿足端高度落在 `feet_clearance_target = 0.05 m` 与 `feet_clearance_cap = 0.09 m` 之间时给满分，**超出 cap 后按同样斜率在一倍跨度内衰减回 0**（0.13 m 以上完全不给分），且整体**钳制在 ≥0**。拖地的脚得 0 分、抬起的脚得正分，所以策略没有"索性不抬腿"的动机；抬过头也没有额外收益，所以也没有"越抬越高"的动机。权重 `feet_clearance = 0.3`：该项是速度追踪的**从属项**——初版取 1.0 时它一度占到总奖励的约 85%。
  早期版本在 cap 处封顶后一直保持满分（没有衰减段），于是没有任何力量把过高的脚压回来：实测空中脚有 95% 超过 cap、摆动腿高度中位数 0.157 m（cap 为 0.09 m），机器人高抬腿踏步，站住不动时也一样。改成"带"以后，把同一个旧步态分别按两种形状打分，旧形状 0.739/s、新形状仅 0.056/s——**丧失约 0.68/s，相当于总奖励的 36%**，梯度方向随之反转。
- 其余奖励保持基类默认：`tracking_ang_vel = 0.5`、`action_rate = -0.01`。`feet_air_time` 由基类的 `1.0` 改为 **`0.0`**（关闭）：基类阈值写死 0.5 s，而本机实测摆动腿腾空时间仅约 0.15 s，于是每次落地都扣分，唯一能减少扣分的办法是把腿抬得更高——方向上和高抬腿是同一个推力。实测它只占总奖励的 0.4%（−0.007/s），量级上无关紧要，但方向有害，故直接归零；`feet_clearance` 已以正确的符号覆盖了同一件事。

以上改动了奖励函数，`logs/flat_ybt/` 下的旧检查点需重新训练。

48 维观测依次为：机身线速度 3、机身角速度 3、重力方向 3、速度命令 3、关节位置偏差 12、关节速度 12、上一动作 12。当前不包含步态相位。
默认每迭代采集 `12288 × 24 = 294,912` 条转换；1500 次迭代共 `442,368,000` 条。
**1500 是训练预算，不保证固定次数后就能获得理想步态。** 用 Play 检查站立、前后移动、侧移、转向与抗扰表现后，再决定是否继续训练或调整奖励。

## 4. 怎么启动

在仓库根目录，使用已有 `unitree-rl` 环境：

```bash
conda activate unitree-rl
cd /home/yh/unitree_rl_gym

# 正式训练：默认 12288 环境、1500 次迭代
python legged_gym/scripts/train.py --task=ybt --headless

# 显存紧张时，可以减小并行数量
python legged_gym/scripts/train.py --task=ybt --num_envs=4096 --headless

# 查看正式训练结果并导出 actor
python legged_gym/scripts/play.py --task=ybt --num_envs=16
```

检查点保存在 `logs/flat_ybt/<日期时间>_<run_name>/model_<iteration>.pt`。
Play 的导出文件为 `logs/flat_ybt/exported/policies/policy_1.pt`。
新任务默认从头训练，不会自动加载任何预训练模型。

继续某次训练可显式指定 `--resume --load_run=<运行文件夹名> --checkpoint=<编号>`。
既有训练入口和 Play 不需要为 YBT 改动。

## 6. 带臂版 `ybt_arm`（第一阶段：先走起来）

带臂四足（YBT + RM65-B 机械臂，总质量 68.84 kg）是第二个任务，任务名 `ybt_arm`，
实验目录 `logs/flat_ybt_arm/`。第一阶段的目标只要**正常走路**，所以这一版的原则是
「除了必须变的，什么都不变」，让学习问题尽可能等同于无臂版——机械臂先当配重。
等这一版走起来了，再谈解冻机械臂。

### 6.1 两个任务的区别

| | `ybt` | `ybt_arm` |
| --- | --- | --- |
| 资产 | `resources/robots/ybt/urdf/ybt.urdf` | `resources/robots/ybt_arm/urdf/ybt_arm.urdf` |
| 质量 | 61.67 kg | 68.84 kg（多 7.17 kg 机械臂） |
| 可动关节 | 12 | **18**（多 6 个机械臂关节） |
| 动作 / 观测 | 12 / 48 | **18 / 66** |
| 机械臂 | 无 | 冻结当配重，折叠加贴在背部 |
| 奖励 / 命令 / 地形 / 腿的 PD 增益 | — | **完全继承，一个字都没重写** |
| 实验目录 | `logs/flat_ybt/` | `logs/flat_ybt_arm/` |
| 4096 环境采集速度 | ~145k steps/s | ~97k steps/s（多 7 个网格碰撞体） |

观测仍是 `12 + 3 × 动作数`，即关节位置 18、关节速度 18、上一动作 18。机械臂那 6 维
动作**仍然存在**，只是被乘成 0。

### 6.2 机械臂是怎么冻结的

`LeggedRobot._compute_torques` 把策略动作乘上 `self.action_scale`。基类里这一项是从
`control.action_scale` 铺出来的**逐关节向量**，`YBTArmRobot._init_buffers` 按关节名找到
机械臂那六维、改成 `control.arm_action_scale = 0.0`，于是它们的力矩退化成

```text
p_gains × (default_dof_pos − dof_pos) − d_gains × dof_vel
```

也就是**目标恒为 `default_joint_angles` 的 PD 持位，策略输出对它完全无效**。
机械臂被按住的那个角度就是 6.3 的折叠姿态。

想解冻就把 `arm_action_scale` 改成腿的值（0.25），再给机械臂加奖励项，其余部分不用动。

### 6.3 折叠姿态

六个关节不全为 0，而是折起来贴在背部（`arm_joint_2 = +1.0`、`arm_joint_3 = +2.0`、
`arm_joint_5 = +0.8`，其余 0）。这样机械臂的最低点从 +0.240 m 降到 +0.140 m、质心高度
从 +0.552 降到 +0.321 m、绕躯干原点的二阶矩从 1.918 降到 0.742 kg·m²（降 61%）。

有意思的是**零位其实是静平衡的**（质心正好落在躯干竖轴上，六个关节重力矩全为 0），
所以折叠不是为了省力矩，而是为了降低转动惯量和高度；代价只是肩关节多了一个
7.1 N·m 的恒定负载（占 60 N·m 上限的 12%）。

完整数据和「怎么量出来的」见 [resources/robots/ybt_arm/README.md](../resources/robots/ybt_arm/README.md)，
随时可以用只读脚本复核：

```bash
python resources/robots/ybt_arm/tools/folded_pose.py
```

### 6.4 机械臂的 PD 增益：一个坑

六个机械臂关节**不能共用一组增益**。按 URDF 算出的质量矩阵对角元是
`0.157 / 0.127 / 0.088 / 0.0039 / 0.0019 / 0.0 kg·m²`，从底座往外越来越小。200 Hz
物理步长下 PD 的稳定上界是

```text
k < 4M / dt²       d < 2M / dt        （M 为该关节惯量，dt = 0.005 s）
```

所以最初那组 `k=150 / d=5` 在手腕上远超上界：`arm_joint_6` 的 M 是 0，**任何**非零 k
都越界，实测以 3.9 rad/s 一直抖；同时 `k=150` 对 0.13 的肩关节又偏软。

现在的做法是按每个关节自己的惯量（再加上 0.002 kg·m² 的**转子惯量**
`control.arm_armature`）统一取固有频率 `w = 55 rad/s`、临界阻尼：

```text
k = w²M    d = 2wM
k = [480, 390, 270, 18, 12, 6]      d = [17.5, 14, 10, 0.65, 0.45, 0.2]
```

两个要点：

- **转子惯量是必须的**，不是调参技巧：关节质量矩阵对角元为 0 时 k 的上界就是 0，
  没有它 `arm_joint_6` 无解。它对真实 RM65-B 同样有意义——手腕上主导的就是伺服电机的
  转子惯量。它只加在机械臂六个关节上（`YBTArmRobot._process_dof_props`），
  **腿保持无臂版的 0，所以腿的动力学一点没变**（膝关节惯量只有 0.00216，加 0.002 会让
  站姿软 28%，那正是不能动的）。
- **「抖就抬阻尼」在这里是错的**：d 也有上界 `d < 2M/dt`，手腕上抬阻尼反而更抖。
  这两条上界都写进了 `tests/test_ybt_arm.py`。

### 6.5 怎么启动

```bash
# 训练
python legged_gym/scripts/train.py --task=ybt_arm --headless

# 查看 / 导出
python legged_gym/scripts/play.py --task=ybt_arm --num_envs=16

# 可选的无界面短测（物理 + PPO + 存档 + TorchScript）
python legged_gym/scripts/check_ybt.py --task=ybt_arm --num_envs=64 --max_iterations=3
```

顺序建议：**先照无臂版的配方跑，别急着调参。** 带臂版继承了无臂版那套已经能走的奖励，
所以第一次只需要确认它能走。只有出现下面两种情况才动参数：

- 站姿塌下去 / 腿力矩长期贴着上限 → 把 `base_height_target` 从 0.50 降到 0.45；
- 机械臂被甩得很厉害 → 才回头看 6.4 那两组数。

### 6.6 实测结果

短测（64 环境）全通过：物理、3 次 PPO、检查点保存/重载、TorchScript 导出与推理 rollout。

**实际步态**：拿 200 次迭代的检查点（`logs/flat_ybt_arm/Oct15_13-35-57_/model_200.pt`）
按固定速度命令跑 500 步（10 s），量实际达到的速度：

| 命令 vx (m/s) | 实际 vx（比值） | 侧向 \|v_y\| | \|偏航率\| (rad/s) | 躯干高度 |
| --- | --- | --- | --- | --- |
| 0.50 | 0.508（1.02） | 0.038 | 0.032 | 0.332 |
| 0.80 | 0.810（1.01） | 0.033 | 0.033 | 0.307 |
| 1.00 | 1.006（1.01） | 0.036 | 0.045 | 0.297 |

命令为 0 时原地不动（0.001 m/s、高度 0.451 m）；10 s 内走的距离和速度对得上
（5.1 / 8.2 / 10.1 m）。**速度追踪准确，没有乱转弯、没有横着跑。**

和**同一训练预算**（200 次迭代）的无臂版对比，避免拿刚开训的去比已经收敛的：

| 命令 vx = 1.0 | `ybt_arm` @200 | `ybt` @200 | `ybt` @1500（收敛） |
| --- | --- | --- | --- |
| 实际 vx（比值） | **1.006（1.01）** | 0.964（0.96） | 0.996（1.00） |
| 侧向 / 偏航率 | 0.036 / 0.045 | 0.026 / 0.034 | 0.017 / 0.014 |
| 躯干高度 | 0.297 | 0.411 | 0.501 |

带臂版在同一预算下速度追踪**反而略好**；侧向晃动略大；高度偏低，但无臂版在 200 次迭代时
也偏矮（0.411，收敛后才到 0.501）——"蹲着走"是训练早期的通病，会随训练站直。
**所以先按无臂版的预算（1500 次）把带臂版跑完，再评价步态**；200 次迭代只用来回答
"能不能走"，答案是可以。

静止站姿下的健康指标（`check_ybt.py --task=ybt_arm`）：

- 机械臂持位：静止时最大偏离 **0.042 rad**（约 2.4°）、速度 0.17 rad/s，最吃力的
  `arm_joint_2` 占力矩上限 **12%**（折起来后要扛 3.80 kg 的远端质量、0.19 m 力臂）。
- 静止时最吃力的关节仍然是后腿膝（**38%**，无臂版 36%）——多出来的 7.17 kg 由腿部自己的
  伸展吸收，机械臂六个关节都没进前四。
- 每次复位后的**落地冲击**会把机械臂甩到 0.08 rad、瞬间顶到力矩上限，约 0.3 s 后归位。
  这是**无臂版也有**的落地反弹（无臂版自己也顶到 57%），不是机械臂引入的：两个任务躯干都从
  0.55 m 落下、弹到 0.41 m，最后稳在 0.377 m。
- 静止躯干高度 0.376 m，比无臂版的 0.380 m 低几毫米——就是那 7.17 kg 的差值（两次测量的
  窗口不同会差 1~2 mm，别当精确值看）。

奖励曲线对照（带臂版那次 200 次迭代训练，4096 环境、156 s，与无臂版**同迭代数**）：

| 迭代 200 | `ybt_arm` | `ybt`（无臂） |
| --- | --- | --- |
| episode 长度 | 1002（跑满） | 1001 |
| 速度追踪奖励（权重 1.0） | **0.965** | 0.963 |
| `feet_clearance` | 0.178 | 0.333 |
| `torques` | −0.159 | −0.111 |
| `mean_reward` | 24.98 | 31.06 |

结论：**同迭代数下速度追踪和存活已经和无臂版持平**，落后的两项正好是背着 7.17 kg 的
预期代价（更费劲、脚抬得更低）。200 次迭代远不是收敛结果，`mean_reward` 的差距主要来自
这两项，按无臂版的预算继续训即可。

## 7. 站立平衡版 `ybt_arm_stand`（第二阶段：四足站住，机械臂干活）

第一阶段（第 6 节）里机械臂是被按住不动的配重，策略只学走路。第二阶段换一个问题：
**四足不许走**——腿的唯一任务是把机身稳住、保持水平；**机械臂按脚本自己摆动**，模拟作业动作。
扰动**从 0 开始逐渐加大**（课程），先易后难，允许腿原地小步调整。

任务名 `ybt_arm_stand`，实验目录 `logs/flat_ybt_arm_stand/`。

### 7.1 与 `ybt_arm` 的区别

| | `ybt_arm`（走路） | `ybt_arm_stand`（站着） |
| --- | --- | --- |
| 资产 / 动作 / 观测 | 18 / 18 / 66 | **完全一样** |
| 机械臂的 PD 参考 | 恒定 = 折叠姿态 | 由脚本在「折叠姿态 ↔ 作业姿态」之间驱动 |
| 速度命令 | 随机 0~1 m/s | **全部为 0**（两个追踪奖励自动退化成「别动」） |
| `feet_clearance` 奖励（0.35） | 奖励把脚抬到 0.05~0.09 m | **0.0** —— 站着不该被奖励抬脚 |
| `push_robots` 外力推动 | 开 | **关** —— 扰动只留机械臂，课程指标才干净 |
| 腿的 PD 增益 / 其余奖励项 / 地形 | — | **完全继承，一个字没改** |

机械臂的**六个 PD 增益**在这个任务里是改了的，理由见 7.4。

### 7.2 机械臂是怎么被驱动的

策略那 6 维输出仍然被乘 0（「冻结」的语义和第一阶段完全一致），变的是 **PD 的参考角**。
做法是在子类里给机械臂那 6 列加一个**加性偏置**，数学上和「把参考角换掉」严格等价：

```text
p·(ref − pos) − d·vel  ≡  [p·(home − pos) − d·vel]  +  p·(ref − home)
                            └── 基类现在算的 ──┘        └── 子类加的 ──┘
```

所以基类一行都不用改。**为什么不干脆把脚本写进 `default_dof_pos`？**（我原本打算这么干，
复核后推翻）因为观测里机械臂那 12 维是 `(dof_pos − default_dof_pos) × 1.0`：

* 一旦把参考也写进去，这一维就变成**跟踪误差**——PD 跟得好时只有 0.01~0.03 rad，
  **和噪声（0.01）同量级**，策略等于**看不见机械臂在干什么**；
* 保持 `default_dof_pos` = 折叠姿态，这一维就是机械臂**偏离折叠姿态的真实角度**
  （满幅能到 0.3~0.5 rad），信噪比约 35:1，策略看得清相位、能预判来势。

轨迹是折叠姿态到作业姿态之间的**一次缓入缓出往返**：

```text
q_ref(t) = home + arm_scale · (op − home) · (1 − cos(2π f t + φ)) / 2
```

* `f = 0.5 Hz`（2 s 一个来回，一回合 10 次），远低于 PD 闭环带宽（~55 rad/s），跟得上、不失真；
* `arm_scale ∈ [0, 1]` 就是**课程**。`arm_scale = 0` 时轨迹逐字等于折叠姿态——
  **和第一阶段训练时那个环境一模一样**，这是热启动能用的根本原因（7.6）；
* `φ` 每个环境在初始化时随机一次、**复位时不重置**：12288 个环境相位互不相关，每个
  rollout 都覆盖整个周期。若相位同步，rollout 只有 `24 × 0.02 = 0.48 s`，
  一个 iteration 只能看到 1/4 个周期，优势估计会退化。

相位每个**策略步**（50 Hz）推进一次，不是每个物理子步（200 Hz）——一次策略步里推进 4 次
就等于把频率调成 4 倍。20 ms 的台阶加在 2 s 周期的正弦上足够平滑。

### 7.3 「作业姿态」和它的行程（这个任务真不真实，全在这一节）

机械臂可动质量 5.31 kg、整机 68.84 kg（**7.7%**），支撑域半宽约 0.15 m。所以：

* **惯性反力** `I·α ≈ 0.9 N·m`，对比让整机翻倒需要的 `68.84 × 9.81 × 0.15 ≈ 100 N·m`，
  **约 1%** —— 等于没有扰动；
* 真正有效的通道是**质心偏移**：机械臂质心水平走 `D`，机身质心就偏 `0.104 · D`。

结论：**在折叠姿态附近加大幅度是没用的**（那条路上只能挪 0.14 m），
**必须让机械臂真的伸出去**——这也正好对上「模拟进行一些操作」。

作业姿态是**量出来的**，用工具沿折叠↔作业的直线走 21 个采样点：

```bash
python resources/robots/ybt_arm/tools/folded_pose.py --sweep 0.0 -1.5 0.0 0.0 0.8 0.6
```

| s | 最低点 z | 质心 x | 质心水平行程 | 最吃力关节 |
| --- | --- | --- | --- | --- |
| 0.00（折叠） | +0.140 | −0.137 | 0.000 | `q2` 16% |
| 0.50 | +0.292 | −0.019 | 0.118 | `q3` 13% |
| 1.00（作业） | +0.298 | +0.236 | **0.373** | `q2` 31% |

* 质心水平行程 **0.373 m**（脚本的门槛 0.30 m）→ **机身质心移动 2.9 cm**；
* 全程离躯干碰撞盒顶面最近 +0.050 m、离地最近 +0.140 m，不碰；
* 最吃力的是肩 `q2`，占 60 N·m 上限的 31%；
* `q2 = −1.5` 是肩关节「再往前抬也不远了」的位置（`−1.8` 量出来还是 0.373 m），
  而让 `q1` 横向扫反而**缩短**行程（0.296 m）并把机械臂推到腿上（|y| = 0.52 m）。

**这个扰动到底有多大（实测）**：同一批机器人，把机械臂分别停在行程的两端，
前脚支撑力从 195 N 抬到 **224 N（+42 N）**，四脚合计 675 N；躯干俯仰差 **0.5°**。

**要诚实看待这个数字**：42 / 675 = **6%**，是真扰动，但**不大**——一个本来就能站住的站姿
不费什么力就吸收了。这是资产本身给的上限（2.9 cm 的机身质心位移），不是参数没调好。
想再加难度只有三条路：给工具加配重、提高摆动频率（惯性反力 ∝ f²，但量级仍然小）、
或者把外力推动重新打开。

### 7.4 机械臂的 PD 增益：走路任务那组会让它「振铃」

让机械臂**动起来**，才暴露出按一个固定姿态时看不见的问题。用走路任务那组增益、把机械臂停在
作业姿态（频率 0）、32 个环境、什么都不动它：**没有任何接触，加转子惯量也没用**，
`arm_joint_3` 却一直以 **3.17 rad/s** 振，吃掉 30 N·m 上限的 **86%**；`j2` / `j5` 是
1.20 / 2.37 rad/s（腿只有 0.18 rad/s，不是腿在晃它）。

这是**显式积分的阻尼项越过稳定界**：`d·dt / I < 2`，`dt = 0.005 s`，
而这些关节的实际惯量比 URDF 质量矩阵对角元小。它还**不是「推」机器人，是「晃」机器人**：
同一个振铃把机械臂甩到参考角后面 0.12 rad，并在躯干上激起 19 Hz 的振动。

处理（**只改机械臂那 6 对增益，腿逐位不变，`ybt_arm` 任务一个字没动**）：

* **阻尼降到 1/4**：振铃完全消失，同一个姿态下 `arm_joint_3` 只吃上限的 13%（就是重力负载）。
  降一半（1/2）**照样振**（3.14 rad/s、57%），所以 1/4 稳稳在正确的一侧；
* **刚度抬到 2 倍**：把降阻尼丢掉的跟踪精度补回来。整周期（0.5 Hz）实测**平均误差 0.014 rad、
  最差 0.14 rad**，最吃力关节 `arm_joint_2` 平均占上限 49%。
  只抬到 2 倍是**故意的**：3 倍时最差误差 0.12 rad、`j2` 平均占 52%，
  多给的权限几乎换不来精度，留着备用。

`check_ybt.py` 里对这条的判据是**跟踪误差 < 0.15 rad**，不是 0.05：0.15 这个数也是量出来的
（稳定后平均 0.016、最差 0.04，落地那一下会把某个关节踢到 0.1 持续几步）。
它的作用是抓**机械臂彻底跟丢参考**那种故障（曾经出现过的加法偏置 bug 让误差到 4.2 rad），
不是卡精度。

### 7.5 课程门槛

`arm_scale` 在 `reset_idx` 里涨：先累加刚结束回合的统计，**每 2 s 评估一次**，
**三个门槛全过**才 `+= 0.02`（上限 1.0）：

| 门槛 | 含义 |
| --- | --- |
| 平均回合长度 ≥ 0.9 × 满 | 没摔 |
| 每秒 `tracking_lin_vel` ≥ 0.8 | 没挪窝 |
| 每秒 `orientation` 代价 ≤ 0.02 | 机身够平 |

**单位必须说清楚**：`_prepare_reward_function` 把每个非零权重乘上 `dt`，`compute_reward`
把它累加进 `episode_sums`，`reset_idx` 再除以 `max_episode_length_s = 20 s`。对一个满长回合
（1000 步 × 0.02 s），两个 `dt` 正好抵消，所以日志里的 `rew_orientation` 就是
**每步的 `-E[tilt²]`**（不是它的 50 倍）：

```text
门槛 0.02 /步  ⇒  E[tilt²] ≤ 0.02  ⇒  RMS 倾角 ≤ sqrt(0.02) = 0.141 rad = 8.1°
```

（早先这里写过 `sqrt(0.02/50) = 1.15°`，那是把「满回合累加」误当成了「每步累加」。
反证：站立任务迭代 1294 的日志是 −0.00104，按正确换算开根号是 **1.85°**，
同一检查点直接测得 **1.61°**——同量级，差异只来自采样窗口覆盖的相位；
若按 /50 换算只有 0.26°，与直接测量差 6 倍。）

实测参照：训练完的站立策略满幅 0.5 Hz 下 **1.61°**；训练早期（第 190 次迭代、74% 幅）
日志 −0.0131 即 **6.6°**；零动作、腿完全不补偿的满幅被动机器人约 **9~12°**
（随采样窗口覆盖的相位而变）。所以 8.1° 的含义是「机身比训练好的站姿明显更歪，
但已经比完全不补偿强」——**不是**「摔没摔」的判据，那是长度门槛的活。

另外，课程**不会在第一次评估就开涨**：`learn()` 用 `init_at_random_ep_len` 把回合长度随机截断，
最初几秒结束的那些回合太短，过不了长度门槛（也不该过，它们什么都说明不了）。
实测 4096 环境时前 36 次迭代（约 17 s 仿真时间）幅度一直是 0，之后每次评估都涨。

### 7.6 怎么启动

```bash
# 训练（继承 12288 环境 / 1500 迭代的默认）
python legged_gym/scripts/train.py --task=ybt_arm_stand --headless

# 热启动：用第一阶段走路的策略初始化（检查点要复制进新实验目录）
mkdir -p logs/flat_ybt_arm_stand/warmstart
cp logs/flat_ybt_arm/Oct15_21-44-18_/model_550.pt logs/flat_ybt_arm_stand/warmstart/
python legged_gym/scripts/train.py --task=ybt_arm_stand --headless \
    --resume --load_run=warmstart --checkpoint=550

# 查看 / 导出
python legged_gym/scripts/play.py --task=ybt_arm_stand --num_envs=16

# 无界面短测（物理 + PPO + 存档 + TorchScript + 脚本臂跟踪与倾角实测）
python legged_gym/scripts/check_ybt.py --task=ybt_arm_stand --num_envs=64 --max_iterations=3
```

**想看机械臂动得更快**（用来压测腿部稳定性）：`play.py` 有 `--arm_freq` 覆盖项，
不用改任何文件：

```bash
python legged_gym/scripts/play.py --task=ybt_arm_stand --num_envs=16 \
    --load_run=Oct16_13-32-01_ --checkpoint=1250 --arm_freq=1.0
```

实测（`model_1250`、64 环境、机械臂满幅）——**这个旋钮不是越大越狠**：

| 频率 | 躯干 RMS 倾角（停住 → 摆动） | 机械臂跟踪误差 平均/最大 | 关节峰值速度 | 四脚接触占空比 |
| --- | --- | --- | --- | --- |
| 0.50 Hz（任务默认） | 1.40° → **1.61°** | 0.014 / 0.148 rad | 3.21 rad/s | 100% |
| 1.00 Hz | 1.28° → **3.00°** | 0.178 / 1.175 rad | 4.01 rad/s | 100% |
| 2.00 Hz | 1.33° → **2.02°** | 0.246 / 1.515 rad | 3.45 rad/s | 100% |


1 Hz 才是真正的压测（倾角翻倍到 3°，机械臂开始明显跟不上参考）；**到 2 Hz 反而变轻**，
因为 PD 已经追不上参考，机械臂的实际摆幅塌了——扰动在 1 Hz 附近最大。另外 1 Hz 时关节峰值
速度是 4.0 rad/s，超过 RM65-B 的 3.14 rad/s 上限，所以 0.5 Hz 以上都只能算「压测」，
不是真实机械臂能做出的动作。三种频率下四只脚都 100% 踩在地上，腿靠柔性吸收，不抬脚。

**热启动为什么合法**（回答「锁死臂练出来的 550 策略能当热启动吗」）：能，而且是这个任务里
最合适的一次。观测宽度完全一致（66），网络不用改；腿那一套（站住、保高度、保水平、
扛住 7.17 kg）**全部继承**；`arm_scale = 0` 时注入项恒为 0，环境与被训练时**逐字相同**，
然后课程再一点点把机械臂摇起来。真正要重新学的只有「对机械臂晃动的反应」。

三个会让人意外的地方：

1. **优化器的 Adam 动量也是从走路任务带过来的**，前几次更新偏大——正常，几十步就消化了；
2. **迭代号从检查点里接着数**：从 550 恢复，日志就是 `550/1700` 这样往上打印，
   所以 `--max_iterations=1500` 的意思是**再跑 1500 次**（到 2049）；
3. **ETA 是按「从头跑」估算的**，恢复训练时会严重偏小（实测报了 411 s，实际要 45 min 上下）
   ——别看 ETA，用「迭代时间 × 剩余迭代数」自己估。

### 7.7 实测：热启动 200 次迭代

4096 环境、159 s、从 `model_550` 热启动（`--max_iterations=200`）：

| 迭代 | `arm_scale` | 回合长度 | `tracking_lin_vel` | `orientation`（每秒） | RMS 倾角（√E[tilt²]） | `mean_reward` |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 0.00 | 13 | 0.011 | −0.0000 | ~0° | 0.23 |
| 40 | 0.02 | 972 | 0.941 | −0.0034 | 3.3° | 23.23 |
| 100 | 0.32 | 989 | 0.965 | −0.0077 | 5.0° | 24.88 |
| 190 | 0.74 | 978 | 0.967 | −0.0131 | 6.6° | 25.12 |

第 0 行是刚加载时的**残段回合**（长度 13），别当性能看。

读法：

* **课程确实在爬**：0 → 0.78，而且从第 37 次迭代起**每次评估都涨**——
  39 次评估正好涨了 39 个 0.02，说明三个门槛一次都没拦它；
* **腿顶得住**：回合长度一直贴着 1000（满），速度追踪奖励 0.94~0.98，没有站不住的迹象；
* **代价在倾角上看得到**：机械臂摆到 74% 幅，躯干 RMS 倾角从 3.3° 涨到 6.6°。
  这是训练到第 190 次迭代的水平（策略还在适应）；同一个任务训练完的 `model_1250`
  在满幅 0.5 Hz 下直接测得 **1.61°**（7.6 节的频率实测表），说明继续训练会把这段倾角压下去。
  7.3 节用**支撑力**量出的 0.5° 是「机械臂停在行程两端」的静态俯仰差，不含腿的动态调整，
  所以量级更小；
* `rew_ang_vel_xy` 反而从 −0.0120 降到 −0.0084：前期的大值是落地/起步瞬态，
  不是机械臂引起的抖动。

**结论**：这个任务在物理上是成立的（腿确实在为机械臂的晃动做平衡），但**量级偏温和**——
6% 的负载转移，一个稳站姿吸收它不费什么力。要不要让机械臂干得更狠（加配重 / 提频率 /
开外力推动），是设计选择，不是训练能不能收敛的问题。

## 8. 边走边干活 `ybt_arm_walk`（第三阶段：最难）

第三阶段把前两个任务叠在一起：**机械臂照样按脚本摆动作业，四足同时执行第一阶段那套
速度指令（前进/横移/转向）**，而且 `push_robots` 外力也保留——扰动 = 机械臂 + 推力 + 地面。
任务名 `ybt_arm_walk`，实验目录 `logs/flat_ybt_arm_walk/`。

### 8.1 与另外两个任务的区别

| | `ybt_arm`（第一阶段） | `ybt_arm_stand`（第二阶段） | `ybt_arm_walk`（第三阶段） |
| --- | --- | --- | --- |
| 机械臂 | 冻结成配重 | 脚本摆动 | **脚本摆动** |
| 速度命令 | 随机走/横移/转向 | 全 0 | **随机走/横移/转向** |
| `feet_clearance` | 0.3 | 0.0 | **0.3（继承走路）** |
| `push_robots` | 开 | 关 | **开** |
| 漂移终止 | 无 | 有（`max_drift = 0.6 m`） | **无，走路的机器人本来就该离开原点** |
| 机械臂 PD | 原增益 | ×2 刚度 / ×1/4 阻尼 | **同站立版** |

观测仍是 66 维、动作 18 维，所以第一阶段的 `model_550` 可以直接热启动。

### 8.2 代码结构：两个脚本臂任务是「兄弟」

「机械臂按脚本动」这件事（参考轨迹、相位、力矩重算、复位、课程）和「腿在干什么」无关，
所以抽成了一个共用基类，两个任务平级：

```text
YBTArmRobot                 冻结臂的接线（ybt_arm）
└── YBTArmScriptedRobot     轨迹 + 加性偏置 + 课程 + 复位（共用）
    ├── YBTArmStandRobot     只多一条漂移终止
    └── YBTArmWalkRobot      空类；终止直接用基类
```

配置同理：`YBTFlatArmScriptedCfg` 放 `arm_trajectory` 和重调后的机械臂 PD，
站立版和走路版各自只声明差异。**为什么不看 `ybt_arm_stand_env.py` 里那套直接复制？**
因为复制之后改轨迹或课程要改两处，迟早会漏；而且让 walk 继承 stand 还会把站立的漂移判据
带进来（走路的机器人必须能走远），再手动撤销它只会让以后 stand 的每个新 override
都悄悄漏进 walk。`tests/test_ybt_arm_walk.py` 里有一组**方法同一性**断言，
只要有人把共用代码复制进某个子类，测试就会红。

### 8.3 课程门槛：先量，再定

走路版只在同一轮训练里把 `arm_scale` 从 0 涨到 1.0（和站立版同一套机制），
但**门槛要按走路重新标定**。先用热启动策略直接测（64 环境、随机速度指令、推力开，
各 3000 步）：

| `arm_scale` | `tracking_lin_vel` | `E[tilt²]` | RMS 倾角 | 回合 | 摔倒 |
| --- | --- | --- | --- | --- | --- |
| 0.00（臂停住） | **0.966** | 0.0025 | **2.9°** | 满长（3000 步里只有 1 次摔倒） | 1 |
| 1.00（满幅摆） | **0.555** | 0.0536 | **13.3°** | 平均 **121 步** | **1592 / 1600** |

结论很清楚：**第一阶段策略根本扛不住满幅摆动**（88% 的回合提前摔倒）——这正是要训练
第三阶段的原因；课程必须从 0 慢慢摇上去。两个门槛因此定成：

| 门槛 | 走路版 | 站立版 | 依据 |
| --- | --- | --- | --- |
| 平均回合长度 | ≥ 0.9 × 满 | 同 | **真正的摔倒判据**；满幅未适应时只有 12%，课程会立刻停住 |
| `tracking_lin_vel` | **≥ 0.75** | ≥ 0.8 | `exp(-e²/0.25)=0.75 ⇒ e = 0.268 m/s`；热启动实测 0.966，留足余量 |
| `orientation` 代价 | **≤ 0.08** | ≤ 0.02 | RMS 倾角 ≤ **16.2°**，高于「满幅未适应」实测的 13.3°，否则课程会在第一次满幅评估时被自己卡死 |

**门槛宁可松一点**：太紧的后果是 `arm_scale` 永远停在某个值，整轮训练无声地白跑；
太松只是让幅度按固定节奏（每 2 s 最多 +0.02）涨快一点，策略自己会补回来。
真正的安全网是回合长度门槛。

### 8.4 怎么启动

```bash
# 热启动（第一阶段走路的策略；检查点复制进新实验目录）
mkdir -p logs/flat_ybt_arm_walk/warmstart
cp logs/flat_ybt_arm/Oct15_21-44-18_/model_550.pt logs/flat_ybt_arm_walk/warmstart/
python legged_gym/scripts/train.py --task=ybt_arm_walk --headless \
    --resume --load_run=warmstart --checkpoint=550

# 查看 / 导出（play.py 会自动把幅度拉到满幅）
python legged_gym/scripts/play.py --task=ybt_arm_walk --num_envs=16 \
    --load_run=<run> --checkpoint=<n> --cmd_vx 0.5
python legged_gym/scripts/play.py --task=ybt_arm_walk --num_envs=16 \
    --load_run=<run> --checkpoint=<n> --cmd_vx 0.5 --cmd_heading 90

# 无界面短测（零动作，所以量的是「站着被机械臂推」而不是走路）
python legged_gym/scripts/check_ybt.py --task=ybt_arm_walk --num_envs=64 --max_iterations=3
```

`play.py` 的 `--arm_freq`、`--cmd_*` 这些旋钮和站立版完全一样，因为两个任务共用同一个类。

### 8.5 实测：4096 环境热启动 200 次迭代

| 迭代 | `arm_scale` | 回合长度 | `tracking_lin_vel` | `orientation`（每秒） | RMS 倾角 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0.00 | 12.7 | 0.008 | −0.0000 | ~0°（加载时的残段回合，别当性能看） |
| 49 | 0.0617 | 1002 | 0.956 | −0.0035 | 3.4° |
| 99 | 0.3008 | 993 | 0.941 | −0.0050 | 4.1° |
| 149 | 0.5408 | 1002 | 0.949 | −0.0061 | 4.5° |
| 199 | 0.7800 | 1002 | 0.950 | −0.0075 | **5.0°** |

读法：

* **课程在稳定地爬**：前 ~36 次迭代因为 `init_at_random_ep_len` 的残段回合不涨
  （和站立版一致），之后每 2 s 评估一次、每次都涨，0.02 一步，完全没被门槛拦住；
* **腿扛得住**：速度追踪一直 0.94~0.96，回合长度贴着 1000，没有出现「为了平衡放弃指令」
  或「为了走路摔倒」的迹象；
* **倾角随幅度缓慢上升**（3.4° → 5.0°），远低于 16.2° 的门槛，也低于站立版 200 次迭代时
  的水平——因为走路时腿本来就在动，对扰动的容忍度更高。

**一个要记住的坑**：`arm_scale` 是环境里的课程状态，**不存进检查点**。所以 `--resume`
之后幅度会从 0 重新爬（网络已经会了，爬得很快、也不会摔），日志里的迭代号同样从检查点
接着数。这是设计使然，不是 bug。

### 8.6 正式训练：12288 环境、约 406 次迭代

换成正式配置（`--num_envs=12288`，热启动同一个 `model_550`）后一路跑到满幅，
在约 **406 次迭代**（每次 1.9 s，约 13 分钟）时指标已经平了，按「差不多收敛就停」
停在这里，检查点在 `logs/flat_ybt_arm_walk/Oct17_21-45-46_/model_400.pt`。

满幅之后（第 245 次迭代起）的三个阶段：

| 迭代 | `arm_scale` | `mean_reward` | `tracking_lin_vel` | `orientation` | RMS 倾角 |
| --- | --- | --- | --- | --- | --- |
| 250 | 1.00（刚满幅） | 31.30 | 0.946 | −0.0071 | 4.8° |
| 300 | 1.00 | 31.71 | 0.950 | −0.0059 | 4.4° |
| 400 | 1.00 | 32.17 | 0.950 | −0.0048 | 4.0° |

第 250 → 400 次迭代，奖励从 31.3 涨到 32.1、倾角从 4.8° 降到 4.0°，
最后 30 次迭代奖励变化不到 0.1——策略在满幅下又适应了一轮，然后到平台。

**最终策略直接实测**（`model_400`，64 环境、随机速度指令、推力开、满幅 0.5 Hz，3000 步）：

| | 热启动 `model_550`、臂停住 | 热启动、满幅（未适应） | **训练后 `model_400`、满幅** |
| --- | --- | --- | --- |
| `tracking_lin_vel` | 0.966 | 0.555 | **0.964** |
| `E[tilt²]` / RMS 倾角 | 0.0025 / 2.9° | 0.0536 / 13.3° | **0.0037 / 3.5°** |
| 3000 步内摔倒 | 1 | 1592 / 1600 回合 | **1** |
| 机身水平位移 | 3.38 m | 0.54 m（摔得走不动） | **3.43 m** |

也就是说：**训练后满幅摆动的走路表现，和臂完全停住时几乎一样**
（追踪 0.964 vs 0.966，倾角只多 0.6°，摔倒次数相同，照样能走出 3.4 m）。
这正是第三阶段想要的结果——机械臂干活不再拖累四足的行走指令。
